# 03 — Design: from idea to an approved approach

> 🇻🇳 Thiết kế: từ ý tưởng tới phương án được duyệt.

## When is a design document needed?

> 🇻🇳 Khi nào cần tài liệu thiết kế?

| Write an RFC (design doc) when the change… | Otherwise |
|---|---|
| adds or removes a module, service or table | Describe the approach in the PR |
| changes an API contract used by another app | |
| introduces a new technology, language or infrastructure component | |
| needs a data migration on existing data | |
| is estimated > 6 sessions or has more than one reasonable approach | |

An **RFC** explains *how we plan to build something* and is discussed before code. An **ADR** records *one decision* and its reasons, and is kept forever. A large RFC usually produces one or more ADRs.

> 🇻🇳 **RFC** giải thích *dự định xây thế nào*, được thảo luận trước khi viết code. **ADR** ghi lại *một quyết định* và lý do, giữ mãi mãi. Một RFC lớn thường sinh ra một hoặc vài ADR.

## How to present and confirm an idea

> 🇻🇳 Cách trình bày và xin xác nhận ý tưởng.

1. **Start from the problem**, not the solution: one paragraph a PO understands.
   > 🇻🇳 Bắt đầu từ vấn đề, không phải giải pháp.
2. **Sketch before writing.** A box diagram or a 5-line flow is enough to check that the idea is going in the right direction. Share it early (draft PR) — a 10-minute correction now saves days later.
   > 🇻🇳 Phác thảo trước khi viết dài. Chia sẻ sớm (draft PR) — sửa 10 phút lúc này tiết kiệm nhiều ngày sau.
3. **Show at least two options** with trade-offs, including "do nothing" when relevant, and recommend one.
   > 🇻🇳 Đưa ít nhất hai phương án kèm đánh đổi, kể cả "không làm gì" nếu hợp lý, và đề xuất một phương án.
4. **Name the risks and how to roll back.**
5. **Ask for a decision explicitly**, from the right person (see RACI in [01-team.md](01-team.md)): "TL, please approve option B by Friday."
   > 🇻🇳 Xin quyết định rõ ràng, đúng người, có hạn.
6. **Record the decision** in an ADR; link it from the RFC and the issue.

## RFC structure

> 🇻🇳 Cấu trúc RFC — template ở `docs/templates/design-doc.md`.

1. Summary (3 lines) · 2. Problem and goals / non-goals · 3. Current state · 4. Proposed design (diagrams, data model, API, error handling) · 5. Alternatives considered · 6. Migration / rollout / rollback · 7. Testing plan · 8. Security, performance, operations impact · 9. Open questions.

## Diagrams

> 🇻🇳 Các loại sơ đồ — dùng Mermaid trong Markdown để GitHub hiển thị trực tiếp và review được qua diff.

| Diagram | Use it for | Tool |
|---|---|---|
| **C4 context / container** | Where the system sits, which services exist | Mermaid `flowchart` |
| **ERD** | Tables, keys, relationships | Mermaid `erDiagram` (generated from the DB, then trimmed) |
| **Sequence** | A request crossing several components (auth, upload, queue) | Mermaid `sequenceDiagram` |
| **State** | Lifecycle of an entity (draft → published → archived) | Mermaid `stateDiagram-v2` |
| **API contract** | Endpoints, payloads, errors | OpenAPI (`laravel-api/openapi.json`, generated by Scramble) |

Rules: one diagram answers one question; keep it under ~15 boxes; diagrams live next to the text that explains them.

> 🇻🇳 Quy tắc: mỗi sơ đồ trả lời một câu hỏi; dưới khoảng 15 khối; đặt cạnh phần chữ giải thích.

## ADR rules

- One decision per ADR, numbered `ADR-nnnn`, template [docs/templates/adr.md](../templates/adr.md).
- Status: Proposed → Accepted; later Superseded / Deprecated. Accepted ADRs are not edited — a new ADR supersedes them.
- Any new tool, language, framework or infrastructure component needs an ADR that names the problem it solves ([ADR-0001](../adr/0001-engineering-lab-direction.md)).

> 🇻🇳 Mỗi ADR một quyết định; ADR đã Accepted không sửa; mọi công nghệ mới phải có ADR nêu vấn đề nó giải quyết.

## Result in one line

Of the statements behind seven hot endpoints (54 logged, login included), **two are slow, both search on `evidence`**: the trigram fallback (33–57 ms, a sequential scan — the GIN trigram index is never chosen) and the full-text query (7–10 ms, `ts_rank` recomputes `to_tsvector` for every match). Everything else runs under 1 ms, except a schema lookup (`Schema::hasColumn`, ~1.5 ms) that every admin list request makes needlessly. Tried on the perf database: a **stored `tsvector` column** takes full text to 0.3–0.5 ms, a **GiST trigram index** takes the fallback to 0.5–1.3 ms for a typical term (11–16 ms for a term in 25 % of rows).

> 🇻🇳 Trong các câu lệnh của bảy endpoint nóng (54 câu được ghi, tính cả đăng nhập), **chỉ hai câu chậm, đều là search trên `evidence`**: trigram dự phòng (33–57 ms, quét tuần tự — index GIN trigram không bao giờ được dùng) và full-text (7–10 ms, `ts_rank` tính lại `to_tsvector` cho từng dòng khớp). Các câu khác dưới 1 ms, trừ một truy vấn schema (`Schema::hasColumn`, ~1,5 ms) mà mọi request list của admin gọi thừa. Thử trên DB perf: cột `tsvector` lưu sẵn đưa full-text về 0,3–0,5 ms; index GiST trigram đưa trigram về 0,5–1,3 ms với từ khóa thông thường (11–16 ms nếu từ khóa có trong 25 % số dòng).

## Method

- Throwaway `perf` database at the REQ-002 volume (same seed as the baseline: 100 skills, 1,500 evidence, 30 tags, 60 goals), `ANALYZE` after seeding. PostgreSQL 16.15, `shared_buffers` 256 MB, `work_mem` 4 MB, `random_page_cost` 1.1.
- `auto_explain` (`log_analyze`, `log_buffers`, `log_min_duration = 0`) enabled **on the `perf` database only** through `ALTER DATABASE … SET`, then `perf/k6/explain-requests.js` sends each request once: public list and detail, admin search (exact term and typo), skill list, evidence list, dashboard summary. One warm-up round first, so the plans are from warm shared buffers. These are the plans the app really gets, with its parameters.
- `perf/sql/db-01-search-experiments.sql` (replaced by `perf/sql/search-plans.sql` once API-03 shipped the fix; the version used here: `git show 9afa0ad:perf/sql/db-01-search-experiments.sql`) then re-runs the two slow statements with `EXPLAIN (ANALYZE, BUFFERS)` for two terms and tries fixes inside a transaction that is rolled back. Terms: `postgresql` appears in **25 %** of the seeded evidence (the seeder's title word pool repeats every fourth row — a skew, see Limits), `kubernetes` in **5 %**.

> 🇻🇳 DB `perf` tạm với khối lượng REQ-002. Bật `auto_explain` chỉ trên DB `perf` để ghi lại kế hoạch thật của mọi câu lệnh khi gửi mỗi request một lần (sau một vòng làm nóng). Sau đó chạy lại hai câu chậm với hai từ khóa (25 % và 5 % số dòng) và thử các cách sửa trong một transaction được rollback.

## Plans of the hot endpoints

Execution time from `auto_explain` (warm buffers; ranges are three capture runs). Admin requests also make one session-user lookup (`admin_mst` by id, 0.03 ms), not counted below.

| Endpoint | Statements | Slowest statement | Plan of the slowest |
|---|---|---|---|
| `public/skills` | 2 | skills `is_public` ordered by name, 0.21 ms | seq scan + sort of 100 rows |
| `public/skills/{slug}` | 4 | public evidence of the skill, 0.31 ms | nested loop over `evidence_skill` |
| `admin/search?q=postgresql` | 3 + 6 × `unaccent` | **evidence full text, 5.8–10.0 ms** | bitmap scan on `evidence_search_fts` (375 rows) → sort by `ts_rank` |
| `admin/search?q=postgersql` (typo) | 3 full text (no match) + 3 trigram | **evidence trigram, 36.8–47.4 ms** | **seq scan**, 1,125 of 1,500 rows removed by filter, sort by `<<->` |
| `admin/skill/list` | 4 | **schema lookup on `pg_attribute`, 1.5–1.8 ms** | from `Schema::hasColumn` |
| `admin/evidence/list` | 5 | **schema lookup, 1.4–1.7 ms**; `count(*)` 0.36 ms | same |
| `admin/dashboard/summary` | 4 | `count(*) FILTER` on evidence, 0.46 ms | seq scan of 1,500 rows |

Other observations:

- The first `unaccent()` call in a backend costs ~0.6 ms (dictionary load), every later one < 0.01 ms. With a new backend per request (PERF-01) every search pays it once.
- Goal search (`learning_goal` join `skill`, no index on the note text) is 0.5–0.65 ms at 60 goals; it scans and is fine at this size.
- Paginated lists use `limit 15 offset 0` plus a separate `count(*)`; both are below 0.4 ms at 1,500 rows. Not a concern before ~100k rows.

> 🇻🇳 Bảng trên: thời gian thực thi của câu chậm nhất mỗi endpoint. Chỉ search trên `evidence` và truy vấn schema trong list admin là đáng kể. Lần gọi `unaccent()` đầu tiên trong mỗi backend tốn ~0,6 ms (nạp từ điển). Search mục tiêu và đếm/phân trang đều dưới 1 ms ở quy mô này.

## Why the two search statements are slow

**Full text on `evidence`** (`to_tsvector('simple', search_text) @@ …  ORDER BY ts_rank(to_tsvector('simple', search_text), …)`): the GIN expression index finds the 375 matches in ~0.3–0.5 ms, but ranking needs the vector itself, and the index does not store it, so `to_tsvector` runs again on every matching row (~15 µs each). Cost grows with the number of matches, not the table.

**Trigram fallback on `evidence`** (`f_unaccent(lower($1)) <% search_text ORDER BY … <<-> search_text LIMIT 10`): the planner estimates the sequential scan as cheap (it does not cost `word_similarity`, which is ~25 µs per row on these texts) and never uses `evidence_search_trgm`. Forcing the GIN index (`enable_seqscan = off`) gives 11.7–24.3 ms at 25 % and 5.0 ms at 5 %: the index narrows the rows, but each candidate still needs the similarity for the sort, and GIN cannot return rows in distance order.

> 🇻🇳 Full-text: index GIN tìm ra 375 dòng rất nhanh, nhưng `ts_rank` cần tsvector mà index không lưu, nên `to_tsvector` bị tính lại cho từng dòng. Trigram: planner đánh giá quét tuần tự là rẻ (không tính chi phí `word_similarity` ~25 µs/dòng) nên không bao giờ dùng index GIN trigram; ép dùng GIN thì nhanh hơn nhưng vẫn phải tính độ tương đồng cho mọi ứng viên vì GIN không trả về theo thứ tự khoảng cách.

## Experiments (perf database, rolled back)

Execution time in ms; two runs of the experiment file (run 1 / run 2; the second on a busier host, 1.3–2× slower). D and the 5 % GIN case ran only in run 2.

| Statement | `postgresql` (25 %) | `kubernetes` (5 %) |
|---|---|---|
| A. Full text now (expression GIN index) | 6.9 / 9.7 | 1.5 / 2.7 |
| **D. Full text on a stored `tsvector` column + GIN on it** | **0.5** | **0.3** |
| B. Trigram now (seq scan) | 40.9 / 57.4 | 32.7 / 42.1 |
| B. Trigram, GIN forced | 11.7 / 24.3 | 5.0 |
| **C. Trigram with a GiST `gist_trgm_ops` index (KNN `ORDER BY <<-> LIMIT 10`)** | 11.5 / 16.6 | **0.5 / 1.3** |

Storage at 1,500 rows: the stored vector adds ~690 kB to `evidence` (856 → 1,544 kB); its GIN index is 128 kB against 352 kB for today's expression index, which it would replace. The existing trigram GIN index is 1.3 MB.

The GiST index answers `ORDER BY <<-> LIMIT 10` by walking the index in distance order and stops after ten rows, so its cost follows the limit rather than the number of matches — except when many rows sit at similar distance (the 25 % case).

> 🇻🇳 Thử nghiệm: cột `tsvector` lưu sẵn đưa full-text từ 1,5–9,7 ms xuống 0,3–0,5 ms. Index GiST trigram trả kết quả theo thứ tự khoảng cách và dừng sau 10 dòng: 0,5–1,3 ms với từ khóa 5 %, 11–17 ms với từ khóa 25 %. Cột lưu sẵn thêm ~690 kB cho 1.500 dòng; index GIN của nó nhỏ hơn index biểu thức hiện tại.

## Proposals (not applied; each needs the owner's OK)

1. **Search storage** (lane `api`, task API-03; amends ADR-0009): for `skill` and `evidence`, a stored `search_tsv tsvector` generated column (repeating the `search_text` expression, since a generated column cannot read another) with a GIN index replacing `*_search_fts`, ranking on the stored column; and a GiST `gist_trgm_ops` index replacing the GIN trigram index, which the planner does not use. Expected on this seed: full text 7–10 → < 1 ms, typo search 33–57 → 1–17 ms. Re-run `perf/explain.sh` and the baseline after the migration.
2. **Drop the schema lookup from admin lists** (lane `api`, task API-04): `BaseRepository::applySorting()` calls `Schema::hasColumn()` even when `allowedSort()` already checked the column against a list, so every skill / evidence / goal / tag list runs a `pg_attribute` query (~1.5 ms, more on a cold backend). Skip it when the whitelist was applied (or move the remaining callers to `allowedSort()`).
3. **Seed realism** (lane `perf`, task PERF-02): the seeder's title words repeat with period 4, so one term is in 25 % of evidence; that over-states search cost. Spread the word pools before the next baseline, and keep the 25 % term as an explicit worst case.

Nothing proposed for the public endpoints, the dashboard or pagination: all under 0.5 ms here.

> 🇻🇳 Đề xuất (chưa áp dụng, cần owner đồng ý): (1) API-03 — cột `tsvector` lưu sẵn + index GIN, và đổi index trigram sang GiST (bổ sung ADR-0009). (2) API-04 — bỏ `Schema::hasColumn()` thừa trong list admin. (3) PERF-02 — sửa seeder để từ khóa phân bố thực tế hơn. Endpoint public, dashboard, phân trang: không cần làm gì.

## Limits

- One host, three capture runs and two experiment runs; timings vary by 1.3–2× between runs, the order between variants does not.
- 1,500 evidence rows. At the 100× scale of the [search spike](../spikes/search-2026-10-08/README.md) the trigram picture changes (more rows near each distance); repeat before relying on GiST at a much larger volume.
- Plans come from warm shared buffers; every request still opens a new backend (PERF-01), so catalog and dictionary loads add to these numbers in the real request.

> 🇻🇳 Giới hạn: một máy, số lần chạy ít, dao động 1,3–2×; chỉ 1.500 dòng evidence; kế hoạch đo với buffer đã nóng, còn request thật vẫn mở backend mới mỗi lần.

## Result in one line

At 1 user every endpoint is far below the target (p95 45–90 ms). At 10 concurrent users the target **holds, but only just** for search (p95 292–295 ms in three clean runs; one disturbed run 369 ms) and with at least 60 ms margin for the others. Throughput is capped at ~66–69 requests/s by ~28 ms of per-request overhead that is not query time — the first thing to look at in P8.

> 🇻🇳 Với 1 người dùng, mọi endpoint còn rất xa ngưỡng. Với 10 người dùng đồng thời, ngưỡng p95 < 300 ms **vẫn đạt nhưng sát** với search (292–295 ms qua ba lần chạy sạch; một lần bị nhiễu 369 ms), các endpoint khác còn dư ~70 ms. Thông lượng ~66–69 request/giây, bị giới hạn bởi ~28 ms chi phí cố định mỗi request không nằm ở truy vấn — việc cần xem đầu tiên ở P8.

## What the numbers say

- **Latency under load is mostly queueing.** One request costs ~40 ms at 1 user; with 10 users and 8 workers requests wait for a worker, so p50 rises to ~100–125 ms. Search is the slowest because its fuzzy path (typo query) runs a second set of queries.
- **~28 ms per request is not query time.** Same server: `GET /up` (framework, no DB) ≈ 10 ms, `GET public/skills` ≈ 39 ms, while the search spike measured the queries themselves at < 1 ms p95 at this volume ([spike](../spikes/search-2026-10-08/README.md)). Candidates, not yet measured: a new PostgreSQL connection per request, session start + Redis write on every request that carries the SPA `Referer` (the k6 script sends it, so public requests also get a session; real visitors of the public site do not), no config / route cache, and the WSL2 bind-mounted code. Split it with a profile before changing anything (lane `perf`, DB-01 / P8).
- **The headroom is small.** The target holds at 10 concurrent users with no think time, which is far above the real use (one owner, occasional recruiters), but a slower host or a little more work per request would cross it.

> 🇻🇳 Độ trễ khi có tải chủ yếu do xếp hàng chờ worker. Khoảng 28 ms mỗi request không nằm ở truy vấn (route `/up` không DB ≈ 10 ms, `public/skills` ≈ 39 ms, còn truy vấn search < 1 ms). Nghi vấn — chưa đo: mở kết nối PostgreSQL mỗi request, khởi tạo session + ghi Redis cho request có `Referer` của SPA, chưa cache config/route, code mount từ WSL2. Phải profile trước khi sửa. Biên an toàn nhỏ, dù 10 user đồng thời không nghỉ đã vượt xa mức dùng thật.

## Limits of this baseline

- Built-in PHP server, not nginx + php-fpm: the production path differs (process model, OPcache settings). P4/P8 should repeat this against the production images.
- The public rate limit (60 / min / IP) is neutralised (`CACHE_STORE=array`), because all k6 users share one IP; the 429 behaviour is covered by `PublicSkillApiTest`.
- Everything runs on one host, so k6 competes with PHP and PostgreSQL for CPU; numbers vary by ±5–10 % between runs.
- Read paths only. Writes and the import endpoint (P3-14) are not measured.

> 🇻🇳 Giới hạn: dùng server có sẵn của PHP chứ không phải nginx + php-fpm; rate limit public bị vô hiệu vì mọi user k6 chung một IP; mọi thứ chạy trên một máy nên số dao động ±5–10 %; chỉ đo API đọc.
